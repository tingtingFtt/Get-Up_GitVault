# 传输性能验证

## 可复现的网页方案对照

运行 `npm run benchmark:transfer -- report.json`。固定种子 77，64 个文件、4 MiB 正文，一半随机二进制、一半可压缩数据；本地 HTTP 每个响应等待 15 ms，最多三个读取工作者，不包含 GitHub 限流和真实公网。三种策略均核对所有文件 SHA 与最终 Git 树，失败会退出非零。

2026-10-18 本地 Linux / Node 22 的一次观察：

数值顺序：逐文件基线 / 上一版 ZIP 方案 / 本次方案。

| 场景 | 请求数 | 响应字节 | 耗时 ms |
| --- | --- | --- | --- |
| 首次 | 64 / 1 / 1 | 5,593,472 / 2,107,217 / 2,107,217 | 446.65 / 70.56 / 41.75 |
| 无变化 | 0 / 0 / 0 | 0 / 0 / 0 | 2.24 / 1.44 / 2.89 |
| 更新 4 个文件 | 4 / 4 / 4 | 349,592 / 349,592 / 349,592 | 38.85 / 36.75 / 39.58 |
| 更新 16 个文件 | 16 / 1 / 1 | 1,398,368 / 2,107,220 / 2,107,220 | 118.21 / 30.89 / 28.16 |

这里的比较用于验证首次整包减少请求、小更新只补变化文件，以及保持较小项目原有 ZIP 路径；没有证据表明本次对首次 ZIP 下载有额外固定倍数的提速，不代表真实用户能获得相同速度倍数。零网络场景的毫秒差异主要是本地计算噪声。大于 32 MiB 的项目新增占比判断：若缺失正文不足四分之一则直接补拉，此分支由计划单元测试覆盖，避免为少量小文件重下庞大未变化内容。

CI 使用 Node 22 重新运行并上传原始 JSON，数值会随机器变化。

## APK 原生对照

Android 自动化测试在同一模拟器上暂存 128 个随机文件、8 MiB 正文，再启用保留对象重复暂存。硬性检查：两次读取当前源码均为 8 MiB；首次新写 128 对象，后续新写 0、复用 128；最终树一致；篡改源码仍拒绝；取消仍中断。另用公开仓库固定提交检查冷／热浅获取及内部引用切换，不能使用缓存绕过固定版本。

测试日志中 `GITVAULT_BENCHMARK` 和 `GITVAULT_FETCH_BENCHMARK` 给出实际耗时。测试不向用户仓库推送。仓库既有 float 完整 2,952 文件测试继续执行。模拟器和模型测试不替代具体手机 SAF 提供者与公网环境验收。

## 实机验收

在同一手机、同一授权目录、同一网络、同一固定提交分别测试首次拉取、首次上传、完全不变更新、小范围更新、取消恢复和上传后清理。记录操作日志中的总耗时、原生阶段、缓存命中、新写／复用对象、网页 API 排队／限流等待；不要把累计响应处理耗时误认为纯网络速度。

双设备验收继续覆盖：A 上传／分叉，B 同账号重新导入、比较并恢复固定仓库、修改标签，更新仅写映射分支；再测试改名、同名不同源码、删除重建、账号记录待补写和取消后重试。此项需要两个真实设备和账户授权，不能把自动化模拟当成已在用户设备上完成。
