# Run and deploy your AI Studio app

This contains everything you need to run your app locally.

View your app in AI Studio: https://ai.studio/apps/b4462d66-9b70-4b20-a34a-f5bf543cf034

## Run Locally

**Prerequisites:**  Node.js


1. Install dependencies:
   `npm install`
2. Set the `GEMINI_API_KEY` in [.env.local](.env.local) to your Gemini API key
3. Run the app:
   `npm run dev`

## 项目记录存储与旧数据迁移

- 网页把项目记录按项目存入 IndexedDB，包含固定仓库、分支映射、同步回执和所有历史文件清单；localStorage 只保留小型设置，不再写入 `gitvault_repos_v8`。修改一个项目只写入该项目的数据行；批量连续修改会合并等待中的写入。
- 首次打开新版自动迁移 v8／v7 旧记录，事务提交并重新读取校验后才移除原 localStorage 数据，同时在记录数据库中保留迁移原文。迁移失败保留原记录并停止启动，不当作空账号覆盖。APK 继续使用 Android 加密安全存储，移除 WebView 内的完整项目镜像；旧 Token 随加密记录保留。
- 记录保存失败时显示“重试保存记录”和“导出当前记录备份”；当前内存中的变更可先导出。只有记录写入完成后才允许上传后的源码清理。多个网页同时打开时拒绝较旧页面覆盖较新数据，请先导出未保存变更再重新打开。
- 本地目录清理、批量清理和删除可取消：取消会停止剩余工作，并等待原生任务确认停止；已经删除的部分不会自动恢复。目录变动确认弹窗也会随任务取消。归档清理标记、缓存恢复、目标解绑等操作需等记录落盘后才报告完成。
- 启动迁移失败时，若旧项目列表仍可读取，错误页提供“导出可读取记录备份”，保留项目清单、固定目标和历史，移除 Token；原数据继续保留。正常启动成功后释放这份临时恢复内容，避免长期占用额外内存。
- 项目记录数据库与可清除的源码缓存相互独立。清理源码仍保留历史和固定关系；不保证无限容量，IndexedDB／原生存储仍受设备可用空间和浏览器策略影响。网页在记录尚未写入时提示离开风险，强制结束进程仍可能丢失最后尚未完成的写入。

## 完整项目同步与版本缓存

源码支持可选的 Git 推送／拉取服务，GitHub API 继续管理仓库、Fork 与账号记录。部署方法、网页／APK 配置和分支历史策略见 [Git 传输说明](docs/GIT_TRANSPORT.md)。GitHub Pages 不会自动提供此服务；未配置时继续使用 REST。

使用 Node.js 22，执行 `npm ci` 安装锁定依赖。`npm run lint` 检查类型，`npm test` 运行同步、存储和页面操作回归测试。

- 首次获取会固定源提交 SHA，校验完整文件清单和每个 Git blob；优先下载压缩包，失败时切换到 GitHub 文件接口。请求有超时，操作可取消。
- 浏览器会暂存已校验的下载片段；重试同一提交时复用已完成的文件。目录很多时完整遍历截断的 Git tree；目录导出不再截取前 100 个文件。
- 缓存按项目、提交和文件内容保存。旧版未绑定提交的缓存只有与快照校验一致时才迁移；保存失败会明确报错，不会把内存缓存显示为持久保存。
- 上传到选定分支时生成完整快照，包括来源已删除的文件；覆盖目标文件状态并保留目标提交历史。并发更新时会重新读取目标，最多接续最新提交重试三次；不使用强推。首次上传和重试都验证目标提交及分支。
- 单次上传可选择保留或清理源码；批量上传开始时也会询问。只有远程验证成功、同步凭据和快照记录已持久保存后，才清理所选版本的源码。文件清单和远程提交链接继续保留。
- GitHub 写入统一排队，相邻写入至少间隔 1.1 秒，读取并发最多 3 个，并为本客户端保留每小时 450 次写入的保护预算。网页同源多窗口通过 Web Locks 协调写入；冷却时间会保存，刷新页面不会清除等待。其他设备仍由 GitHub 限流响应统一约束。
- 收到明确的 403／429 限流响应时暂停队列：优先遵守 `Retry-After`，主额度耗尽时同时遵守重置时间；缺少提示时至少等一分钟，再逐步延长，单请求最多自动重试两次。界面显示等待时间，仍可取消；权限错误、丢失响应和服务器错误不会直接重发写入。等待不占用网络请求超时。
- 中断上传会保留 GitHub 已确认的 blob SHA，按目标仓库 ID 隔离，不存 Token 或额外源码副本。继续上传会重新验证这些对象，只补传未完成文件；记录七天内可复用，GitHub 已回收的对象会重新上传。提交和分支仍按原流程验证成功后才标记完成。
- 上传成功会绑定目标仓库 ID、固定名称、分支和清理选择。单项“更新已绑定仓库”继续更新对应目标；批量首次上传会跳过已有固定目标，不随源项目名称重新建仓。只有点击“修改项目名称”才重命名现有仓库，并同步账号记录和历史链接。同源项目默认更新固定目标；需要另存时使用“另存并切换固定仓库”，验证成功后切换，旧仓库和关系保留。之后“一键更新”会下载新版本、归档旧版本，再同步到该目标；上传失败时保留新文件，可重新上传或再次点击更新重试。尚未配置目标时先下载，使用上传入口选择目标。
- 查看和上传历史版本使用该版本的源码；清理后的文件优先从保存的目标提交读取，不依赖源仓库的当前 HEAD。
- 版本归档可分页获取目标分支的 GitHub 提交，查看、下载、对比和恢复指定版本。恢复以当前目标为父提交生成新提交，旧历史和当前源文件缓存继续保留。
- “当前分支独立副本”保存本地所选提交的准确文件，加入我的项目并记住原始来源；后续更新写入固定目标分支。它是独立仓库，GitHub 原生 Fork 不支持任意非默认分支单独分叉。
- “完整分叉”对原始仓库创建包含全部分支和可达历史的原生 Fork，验证来源及分支齐全后加入我的项目。已有匹配 Fork 可直接关联；同名无关仓库会停止处理。创建超时可稍后重试关联。
- 完整分叉的更新会逐个同步上游分支的完整文件状态，包含删除操作，接续目标提交保留本地历史；新增上游分支自动创建，目标独有分支保留。逐分支显示成功或失败，不把部分完成当作全部成功。

完整分叉保留 GitHub 上的 Git 历史；浏览器中的本地快照不是完整 Git 克隆：保存的是指定提交的文件和本应用同步过的版本，不复制源仓库全部历史。包含子模块或 Git LFS 对象的项目当前会明确提示未能完整获取，不会错误标记为完整下载。

GitHub Pages 使用浏览器直连 GitHub；关闭页面后不会持续执行定时检测。清理浏览器缓存不会删除用户已导出的 ZIP 或文件夹。系统记录备份不包含源码缓存或 GitHub Token；恢复到其他设备后需重新填写凭证并获取源码。

## 批量链接与工作台分支

- 新建链接弹窗切换到“批量导入链接”，严格一行一个项目，支持“备注名  链接”或仅填写链接。备注可以含空格、数字和标点；仅链接时备注保存为空，不自动填写“未备注项目”。支持完整地址、`.git` 地址和 `owner/repo` 简写。
- 批量导入按仓库实际默认分支拉取（例如 `main`、`master`），忽略链接附带的分支。同批重复链接或没有上传／分叉关系的已导入默认分支会跳过；可信账号记录可自动恢复已有目标，旧版或尚未确认的目标先等待用户比较选择。单条失败继续下一条，支持仅重试失败链接、取消后保留已完成项目。私有仓库和限流场景可填写共用 Token 或使用全局 Token。
- 导入后在工作台点击“编辑备注与描述”修改资料；这些编辑不重新下载项目。
- 工作台支持获取分支列表，或直接填写分支名后“切换并重新拉取”。新分支完成校验并持久保存后才切换；失败时保留原分支。原有文件、历史快照、仓库名称及各分支绑定均保留，含 `/` 的分支名也可使用。
- 首次私人仓上传及当前分支副本按来源分支名上传；切换到其他分支后，继续使用同一个已绑定仓库，写入对应的同名分支（缺失时创建）。旧记录里明确指定过的目标分支保持原绑定，切回时恢复；已绑定给另一来源分支的目标不会被覆盖。
- 单次上传、批量上传、一键更新和历史恢复均按来源分支路由。历史记录标明所属分支，跨分支恢复只更新历史版本对应的目标分支。重命名会更新所有分支绑定；导出设置备份会排除各分支 Token。

## 新链接与已有上传／分叉项目对比

- 单个新增和批量导入优先读取当前 GitHub 账号的来源与固定目标记录，也匹配本地原始来源、上传目标和分叉记录。没有账号记录时，分页读取本人仓库，用原生 Fork 的上游 ID、旧版托管说明及来源元数据寻找候选；同名仓库会先自动对比当前来源分支与对应目标分支；唯一候选的完整文件树一致时自动关联。代码不同显示差异，允许沿用关系后再更新、立即更新此分支，或填写新名称上传并固定。多个候选由用户比较选择。仓库列表和来源元数据短时复用，避免批量操作重复扫描相同资料。
- 遇到已有关系时先读取清单、等待选择，再下载文件内容；跳过不重复下载整个项目。点击“对比此项目”读取目标仓库身份和指定分支的完整文件树，显示双方提交、分支映射和新增／修改／删除文件列表。内容、文件模式、符号链接和子模块引用参与比较；上传时生成的元数据文件不计入差异，来源自带的同名文件仍比较。无法读取、身份变化或分叉上游不符时禁止沿用，可重试对比或独立导入。确认后的下载固定在比较时的来源提交，并复用已有且校验一致的本地文件。
- 用户可选择“沿用上传目标”“沿用分叉同步”“独立导入，不关联”或“跳过此链接”。比较不写入项目源码；“沿用”只保存账号绑定，“更新此仓库”及“使用新名称上传并固定”在明确选择后写入对应目标。沿用后固定目标名称、ID 和对应分支，后续使用原有上传、更新或同步入口追加提交并保留历史。完整 Fork 的差异展示针对当前分支，后续分叉同步仍同步全部上游分支。
- 同一来源分支已有本地记录时，沿用会更新该记录并归档旧快照，保留旧缓存和历史；独立导入生成无绑定的新记录，不改已有项目。其他来源分支映射到同名目标分支，缺失时仅标记为待新建；禁止占用其他来源项目或来源分支已绑定的目标分支。
- 新链接指向已记录的目标仓库时，可信账号记录可按反向分支映射恢复原始来源；旧版本地记录在比较后确认。来源文件按比较时的提交固定下载。独立导入则继续跟踪新链接本身。
- 批量导入遇到匹配项目会暂停等待该条选择，再继续下一条。取消会停止等待与读取请求，已完成项目保留，其余链接可重试；不记住或自动复用前一条的选择。

## 批量分叉、更新与响应式布局

- 项目库勾选项目后可执行“批量分叉”“批量更新”“批量分叉同步”。快捷选择会替换当前勾选，只选择搜索和标签范围内的项目，不立即执行任务。
- “仅选未上传”“仅选未分叉”均跳过已有上传／分叉目标、待完成创建或切换记录，以及同一来源在其他项目中的现有关系；目标异常不会被当成从未上传。已上传或分叉的同源项目应使用更新／同步，解除旧关系后才可重新首次操作。快捷选择使用本地已知关系，真正执行时仍核验当前账号及远端仓库。
- “仅选有更新”选择已检测到新版本的项目，可先点“全部检测”刷新。“仅选可分叉同步”选择有正常绑定的完整 Fork 或单分支副本，跳过待创建、待切换及目标异常项；同一完整 Fork 优先选择托管副本一次，单分支副本仍按目标分支分别选择，不要求当前分支已有更新提示（其他上游分支也可能有更新）。
- 批量分叉可选完整来源仓库（全部分支和历史）或当前分支独立私人副本，支持逐项改目标名称；验证成功后加入我的项目。同一来源只固定一个目标仓库，首次上传或任一分叉模式完成后，其他来源分支使用对应分支更新，不再创建其他目标；避免本批不同项目使用同一目标名称。
- 更新与同步使用原有来源和目标绑定，按对应分支追加提交，保留历史。完整 Fork 同一目标的多条管理记录共享传输结果，但各自刷新本地快照。部分分支失败会明确显示失败详情，不显示为全部成功。
- 批量任务固定队列、逐项显示结果，单项失败继续下一项；可取消剩余任务、仅重试失败或取消项。已成功项目不重复执行，已下载文件与验证后的远程记录继续保留。
- 工作台按钮使用可换行的紧凑网格，批量主要操作集中展示，标签、精简和删除收进“更多管理”。长名称、备注、描述和标签会在容器内折行；文件路径在列表内省略，代码在自己的区域滚动，弹窗限制在视口内滚动。保留原背景及配色。
- `npm run test:layout` 在生产构建后使用 Chrome 检查 320、375、480、640、768、1024、1440 像素宽度下的主页、项目库、工作台、历史、日志和各弹窗（合计 259 种状态），包括新链接匹配、比较结果、文件差异、身份错误、远端目标管理与解绑恢复、操作日志、批量上传运行／失败／取消、另存切换创建／比较／错误／续办／旧关系历史、长内容与按钮重叠检测。需要已安装 Chrome，或通过 `CHROME_BIN` 指定可执行文件；CI 在部署前自动执行。检查只使用隔离的合成数据，不向 GitHub 执行上传、分叉等写操作。

## 远端仓库被删除或失去权限后的恢复

- 进入工作台、检测更新和上传／同步前会检查已绑定目标，状态保存在项目记录中，并在项目库及工作台显示异常提示。“管理远端目标”可重新检测指定目标或全部目标。账号同源发现独立于这项检测。
- 404 显示为“可能已删除、改名或 Token 无权限”，不据此自动解绑。无效 Token、权限不足、请求限流、网络错误和同名仓库 ID 变化分别提示；临时失败与取消不会自动删除绑定。通过旧地址访问到同一 ID 的改名仓库时更新链接；同名不同 ID 的新仓库禁止自动写入。
- 更新 Token 并重新检测，仅对身份验证成功的目标保存新凭证，供共享该目标的各分支／分叉绑定使用；不改全局或来源凭证。配置导出不包含目标 Token。
- 确认旧目标不再使用后，点击“解除此目标的所有绑定”。确认提示会显示关联记录数量，只解除该远端目标的当前上传、分支和分叉关联；其他目标、项目记录、原始来源、本地源码和历史快照均保留。历史地址不改写到新仓库，也不会从历史副本中自动重新关联已解除的目标。解绑前再次检测，原仓库仍可访问时禁止解绑后重复首次上传。只有确认原仓库删除或原 ID 失效后才解除账号来源记录；远端写入失败会保留待解绑任务，下次创建前必须先完成。
- 解除后可直接“重新设置上传”或“重新创建分叉”，默认带入旧目标名称并允许修改；重新创建的仓库按新 ID 绑定。管理中的旧 Fork 保留项目 ID、来源和本地历史，转为继续跟踪原始来源。新上传继续遵循来源分支和验证成功后才能清理缓存的规则。
- 旧远端版本不可访问且源码缓存已清理时，尝试按保存的源提交恢复，并校验文件清单、hash、类型和模式。源提交也不存在时保留快照、说明需要旧缓存／导出文件或恢复旧仓库，不把未恢复的文件显示为已上传。新仓库只能保留此后产生的 Git 历史，不能凭快照重建用户从 GitHub 删除的全部提交历史。

## 账号去重、跨设备识别与取消日志

- 首次上传、当前分支副本和完整 Fork 共用账号级来源索引。同一来源仓库（优先以 GitHub 仓库 ID 识别）固定一个目标，各来源分支记录自己的目标分支。批量首次上传／分叉跳过已完成或已绑定的同源目标，后续执行“批量更新”或“批量分叉同步”。同名旧仓库先比较；完整文件树一致且唯一时自动绑定，存在差异时用户可更新此仓库或指定新名称另存。独立导入仍可保留本地记录。
- 应用会在当前账号创建私人仓库 `.gitvault-state`，在 `gitvault.json` 中保存来源、目标仓库 ID、分支映射、已验证提交和首次任务预留。不会保存 GitHub Token 或项目文件，不向完整 Fork 源码加入索引文件。不要公开、删除或手动改写这个记录仓库；被其他用途占用、格式损坏或权限不足时会明确停止写入，不将读取错误当作“没有同源仓库”。
- 同账号在其他设备配置 Token 后，新增原始链接或已记录的目标链接会恢复固定目标；远端提交与凭据吻合时显示“已同步”或“已分叉”，否则显示已绑定／待更新。旧版记录可根据 Fork 上游或托管元数据寻找候选并比较迁移。对于没有来源记录且被任意改名的旧仓库，尝试读取各分支的来源元数据；仍无来源证据时，需要通过另存窗口明确选择已有仓库并比较。
- Token 需要能读取当前账号仓库，并能创建私人仓库和写入目标及 `.gitvault-state` 内容；限制到少数仓库的凭证必须包含这些仓库并具备相应写权限。没有 Token 时仍可公开拉取，但无法保证跨设备识别；上传或分叉前必须完成账号检查。
- 创建项目之前先以 GitHub 文件 SHA 的比较并交换保存来源预留，避免两台设备同时选择不同目标；冲突时重新合并，不覆盖其他来源或分支。首次任务中断后固定原目标名，若仓库已经出现则先比较；不会换个名称重新创建。后续快照更新仍接续目标最新提交，不强推。账号记录失败时保留已验证远端凭据、固定目标及本地缓存，再次更新只补存记录后继续检查版本。
- 已知目标 404、限流或网络错误都不会自动取消绑定。确认远端已删除后，在“管理远端目标”解除旧目标并完成账号解绑，才重新建立目标；恢复不了的旧 Git 历史不能由浏览器快照重建。
- 批量上传、更新和分叉同步均可“取消剩余操作”。取消会中止正在等待的 GitHub 请求和未开始项目，已验证完成的项目及远端提交保留；已经发送的 GitHub 写请求可能已在服务器完成，取消不表示回滚。重试只处理失败和取消项，同源去重会在重试前再次执行。
- 顶部“操作日志”在本设备持久保存最近 1000 条结果，可筛选失败与未完成、导出 JSON、清空。记录时间、项目、分支、目标、操作阶段、HTTP 状态与失败原因；已知 Token、Bearer 凭证及常见凭证 URL 会隐藏。日志存储不足会提示，账号绑定仍保存在独立账号记录中；本地日志不跨设备同步。

## 同名代码核验、仓库重命名与另存切换

- Token 确定当前账号；同名查询直接读取该账号下的仓库，不要求 A/B 设备配对或具有同一份浏览器缓存。即使私人改名索引读取失败，能访问的同名仓库仍可完成只读代码核验；文件一致时在本设备恢复绑定，并提示账号记录待补存。读取错误不会被当作“没有已有项目”，账号记录权限恢复前相关写入会明确阻止并保留待办。
- 自动关联依据完整文件树，比较路径、Git blob 内容 hash、模式及引用；跨仓库提交 SHA 不同仍可一致。只有能确认由应用生成的来源元数据才忽略，来源自带的同名文件仍参与比较。私人仓库与原生 Fork 使用实际隐私属性和上游身份设置状态标签，普通副本不会标成 Fork。
- 同名代码不同会展示新增、修改、删除及双方提交。“更新此仓库（保留历史）”只写已确认的当前目标分支；完整 Fork 的全部分支同步保留独立入口。旧记录的自定义分支映射保留，未登记的旧仓库允许先选择正确目标分支再重新比较。
- “修改项目名称”重命名同一仓库，验证 ID 不变，再更新固定名称、地址、主仓库来源、分支及历史链接；操作前重新读取账号固定目标，避免另一设备已切换后误改旧仓库。
- 工作台与上传弹窗提供“另存并切换固定仓库”。展示旧目标 → 新目标，支持创建新私人仓库或选择已有仓库；已有目标先比较。先在账号记录中预留任务，原固定关系继续有效；文件上传核验、账号切换记录及本地记录保存完成后才启用新目标。旧仓库不删除，旧关系和远端快照进入历史，可在工作台查看。
- 另存中断会保留新仓库 ID、固定上传版本、已验证结果与旧绑定。已创建目标的重试需比较；文件已成功而切换记录失败时，“继续完成切换”仅补存关系，不重复上传。其他设备的未完成另存会在写入前恢复为待办，防止并行创建其他副本。
- 首次改名上传以及显式另存切换后，新仓库成为日常拉取的主仓库。原始来源独立保留，“同步上游”继续按原始来源处理；普通更新不会把模板重新覆盖到自己的主仓库。各分支仍分别对应，历史恢复继续追加提交。
- 项目资料和自定义标签随账号记录保存；新设备导入时恢复。普通更新先读取最新资料，避免旧设备上传源码时将另一设备的新标签覆盖。批量标签保存失败时保留本地资料及可重试账号记录。
- 自动测试包含使用真实 registry/GitHub HTTP 适配代码、合成 GitHub 服务模拟的 A 上传／Fork → 清空浏览器记录 → B 导入、同名差异更新、换名上传、标签恢复、重命名、另存部分失败续办、取消以及分支隔离。它们不等同于真实用户账号和两台实体设备验收；未使用用户 Token 创建测试仓库。

## AI 日志与可选服务端

`npm run dev` 使用本地 Node 服务，AI 功能需要服务端 `GEMINI_API_KEY`（可通过 `GEMINI_MODEL` 指定模型）。纯静态 Pages 未配置 AI 服务时，原日志入口提供明确标注的本地提交摘要。

部署独立 AI 后端时，在构建环境设置 `VITE_API_BASE_URL` 为其地址，并由该后端配置正确的来源访问策略。生产同源 Node 部署可在构建时设置 `VITE_API_MODE=server`；运行时使用 `NODE_ENV=production npm start`。GitHub 或 AI 凭证均不应写入静态构建环境的 `VITE_*` 变量。

## 部署

GitHub Actions 使用 `package-lock.json` 和 `npm ci`；PR 自动检查类型、测试和 Pages 构建，main 更新后部署。Pages 构建路径为 `/Get-Up_GitVault/`。

浏览器和 Electron 的现有导出入口继续保留。Android 已接入 Capacitor 工程、应用内异步弹窗、系统目录授权、原生下载与 Keystore 加密存储；打包使用相对资源路径，不影响 Pages 部署。`npm run android:sync` 同步网页和插件，`npm run android:debug` 生成测试 APK。main 的相关变更会触发 **Build Android APK**，输出测试包及正式版构建产物；正式包需配置固定签名。完整步骤与真机验收范围见 [Android 打包说明](docs/ANDROID.md)。

批量导入、上传、分叉、更新、分叉同步和归档发布会逐项保存本设备任务队列，重开后提供手动续办入口；成功项不重复执行，恢复队列不保存 Token。APK 授权目录作为项目主存储，源码按流写入／上传；缓存清理同步删除软件管理的目录文件，保留快照、绑定和 GitHub 历史。独立导出副本自行管理。APK 不保证锁屏后的持续传输，网页更新也不会自动替换 APK 内置资源。

### 同源候选与独立上传

- 同名仓库、旧版元数据和 Fork 父仓库信息属于待确认候选；弹窗会展示匹配依据及可读取的实际来源。旧版元数据仅读取末尾的来源链接，新上传增加明确来源字段，描述和备注里的其他链接不会被当成来源。
- 对待确认候选可选择“这是不同项目，不再关联此候选”，或“独立导入，不关联”。排除结果随本设备项目记录保存，重启后仍生效；按账号、来源、目标仓库身份和匹配依据隔离。目标重建、依据变化或出现已确认的账号绑定时，重新核对。
- 排除无关候选后可以继续以新名称首次上传，或上传到自行指定的其他仓库与分支。目标名称实际已占用时仍需比较和确认；确认过的固定仓库、历史和分支映射不会被排除记录解除。
- 排除不是删除或解除绑定，不会修改候选仓库。此前已经错误确认过的绑定仍需单独核对，不能通过候选排除按钮绕过。
