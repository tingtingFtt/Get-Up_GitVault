# Run and deploy your AI Studio app

This contains everything you need to run your app locally.

View your app in AI Studio: https://ai.studio/apps/b4462d66-9b70-4b20-a34a-f5bf543cf034

## Run Locally

**Prerequisites:**  Node.js


1. Install dependencies:
   `npm install`
2. Set the `GEMINI_API_KEY` in [.env.local](.env.local) to your Gemini API key
3. Run the app:
   `npm run dev`

## 完整项目同步与版本缓存

使用 Node.js 22，执行 `npm ci` 安装锁定依赖。`npm run lint` 检查类型，`npm test` 运行同步、存储和页面操作回归测试。

- 首次获取会固定源提交 SHA，校验完整文件清单和每个 Git blob；优先下载压缩包，失败时切换到 GitHub 文件接口。请求有超时，操作可取消。
- 浏览器会暂存已校验的下载片段；重试同一提交时复用已完成的文件。目录很多时完整遍历截断的 Git tree；目录导出不再截取前 100 个文件。
- 缓存按项目、提交和文件内容保存。旧版未绑定提交的缓存只有与快照校验一致时才迁移；保存失败会明确报错，不会把内存缓存显示为持久保存。
- 上传到选定分支时生成完整快照，包括来源已删除的文件；覆盖目标文件状态并保留目标提交历史。并发更新时会重新读取目标，最多接续最新提交重试三次；不使用强推。首次上传和重试都验证目标提交及分支。
- 单次上传可选择保留或清理源码；批量上传开始时也会询问。只有远程验证成功、同步凭据和快照记录已持久保存后，才清理所选版本的源码。文件清单和远程提交链接继续保留。
- 上传成功会绑定目标仓库 ID、固定名称、分支和清理选择。单项“更新已绑定仓库”继续更新对应目标；批量首次上传会跳过已有固定目标，不随源项目名称重新建仓。只有点击“修改项目名称”才重命名现有仓库，并同步账号记录和历史链接。同源项目已有固定目标时不再允许另存到新仓库；使用更新或同步追加历史。之后“一键更新”会下载新版本、归档旧版本，再同步到该目标；上传失败时保留新文件，可重新上传或再次点击更新重试。尚未配置目标时先下载，使用上传入口选择目标。
- 查看和上传历史版本使用该版本的源码；清理后的文件优先从保存的目标提交读取，不依赖源仓库的当前 HEAD。
- 版本归档可分页获取目标分支的 GitHub 提交，查看、下载、对比和恢复指定版本。恢复以当前目标为父提交生成新提交，旧历史和当前源文件缓存继续保留。
- “当前分支独立副本”保存本地所选提交的准确文件，加入我的项目并记住原始来源；后续更新写入固定目标分支。它是独立仓库，GitHub 原生 Fork 不支持任意非默认分支单独分叉。
- “完整分叉”对原始仓库创建包含全部分支和可达历史的原生 Fork，验证来源及分支齐全后加入我的项目。已有匹配 Fork 可直接关联；同名无关仓库会停止处理。创建超时可稍后重试关联。
- 完整分叉的更新会逐个同步上游分支的完整文件状态，包含删除操作，接续目标提交保留本地历史；新增上游分支自动创建，目标独有分支保留。逐分支显示成功或失败，不把部分完成当作全部成功。

完整分叉保留 GitHub 上的 Git 历史；浏览器中的本地快照不是完整 Git 克隆：保存的是指定提交的文件和本应用同步过的版本，不复制源仓库全部历史。包含子模块或 Git LFS 对象的项目当前会明确提示未能完整获取，不会错误标记为完整下载。

GitHub Pages 使用浏览器直连 GitHub；关闭页面后不会持续执行定时检测。清理浏览器缓存不会删除用户已导出的 ZIP 或文件夹。系统记录备份不包含源码缓存或 GitHub Token；恢复到其他设备后需重新填写凭证并获取源码。

## 批量链接与工作台分支

- 新建链接弹窗切换到“批量导入链接”，严格一行一个项目，支持“备注名  链接”或仅填写链接。备注可以含空格、数字和标点；仅链接时备注保存为空，不自动填写“未备注项目”。支持完整地址、`.git` 地址和 `owner/repo` 简写。
- 批量导入按仓库实际默认分支拉取（例如 `main`、`master`），忽略链接附带的分支。同批重复链接或没有上传／分叉关系的已导入默认分支会跳过；可信账号记录可自动恢复已有目标，旧版或尚未确认的目标先等待用户比较选择。单条失败继续下一条，支持仅重试失败链接、取消后保留已完成项目。私有仓库和限流场景可填写共用 Token 或使用全局 Token。
- 导入后在工作台点击“编辑备注与描述”修改资料；这些编辑不重新下载项目。
- 工作台支持获取分支列表，或直接填写分支名后“切换并重新拉取”。新分支完成校验并持久保存后才切换；失败时保留原分支。原有文件、历史快照、仓库名称及各分支绑定均保留，含 `/` 的分支名也可使用。
- 首次私人仓上传及当前分支副本按来源分支名上传；切换到其他分支后，继续使用同一个已绑定仓库，写入对应的同名分支（缺失时创建）。旧记录里明确指定过的目标分支保持原绑定，切回时恢复；已绑定给另一来源分支的目标不会被覆盖。
- 单次上传、批量上传、一键更新和历史恢复均按来源分支路由。历史记录标明所属分支，跨分支恢复只更新历史版本对应的目标分支。重命名会更新所有分支绑定；导出设置备份会排除各分支 Token。

## 新链接与已有上传／分叉项目对比

- 单个新增和批量导入优先读取当前 GitHub 账号的来源与固定目标记录，也匹配本地原始来源、上传目标和分叉记录。没有账号记录时，分页读取本人仓库，用原生 Fork 的上游 ID、旧版托管说明及来源元数据寻找候选；同名仅作为待比较候选，不能自动认定同源。原本已有的仓库必须比较并由用户确认，不能直接覆盖。仓库列表和来源元数据短时复用，避免批量操作重复扫描相同资料。
- 遇到已有关系时先读取清单、等待选择，再下载文件内容；跳过不重复下载整个项目。点击“对比此项目”读取目标仓库身份和指定分支的完整文件树，显示双方提交、分支映射和新增／修改／删除文件列表。内容、文件模式、符号链接和子模块引用参与比较；上传时生成的元数据文件不计入差异，来源自带的同名文件仍比较。无法读取、身份变化或分叉上游不符时禁止沿用，可重试对比或独立导入。确认后的下载固定在比较时的来源提交，并复用已有且校验一致的本地文件。
- 用户可选择“沿用上传目标”“沿用分叉同步”“独立导入，不关联”或“跳过此链接”。比较不写入项目源码；确认沿用后只保存账号绑定，不自动上传来源文件。沿用后固定目标名称、ID 和对应分支，后续使用原有上传、更新或同步入口追加提交并保留历史。完整 Fork 的差异展示针对当前分支，后续分叉同步仍同步全部上游分支。
- 同一来源分支已有本地记录时，沿用会更新该记录并归档旧快照，保留旧缓存和历史；独立导入生成无绑定的新记录，不改已有项目。其他来源分支映射到同名目标分支，缺失时仅标记为待新建；禁止占用其他来源项目或来源分支已绑定的目标分支。
- 新链接指向已记录的目标仓库时，可信账号记录可按反向分支映射恢复原始来源；旧版本地记录在比较后确认。来源文件按比较时的提交固定下载。独立导入则继续跟踪新链接本身。
- 批量导入遇到匹配项目会暂停等待该条选择，再继续下一条。取消会停止等待与读取请求，已完成项目保留，其余链接可重试；不记住或自动复用前一条的选择。

## 批量分叉、更新与响应式布局

- 项目库勾选项目后可执行“批量分叉”“批量更新”“批量分叉同步”。“仅选有更新”会选中当前筛选范围内已检测到变动的项目。
- 批量分叉可选完整来源仓库（全部分支和历史）或当前分支独立私人副本，支持逐项改目标名称；验证成功后加入我的项目。同一来源只固定一个目标仓库，首次上传或任一分叉模式完成后，其他来源分支使用对应分支更新，不再创建其他目标；避免本批不同项目使用同一目标名称。
- 更新与同步使用原有来源和目标绑定，按对应分支追加提交，保留历史。完整 Fork 同一目标的多条管理记录共享传输结果，但各自刷新本地快照。部分分支失败会明确显示失败详情，不显示为全部成功。
- 批量任务固定队列、逐项显示结果，单项失败继续下一项；可取消剩余任务、仅重试失败或取消项。已成功项目不重复执行，已下载文件与验证后的远程记录继续保留。
- 工作台按钮使用可换行的紧凑网格，批量主要操作集中展示，标签、精简和删除收进“更多管理”。长名称、备注、描述和标签会在容器内折行；文件路径在列表内省略，代码在自己的区域滚动，弹窗限制在视口内滚动。保留原背景及配色。
- `npm run test:layout` 在生产构建后使用 Chrome 检查 320、375、480、640、768、1024、1440 像素宽度下的主页、项目库、工作台、历史、日志和各弹窗（合计 224 种状态），包括新链接匹配、比较结果、文件差异、身份错误、远端目标管理与解绑恢复、操作日志、批量上传运行／失败／取消、长内容与按钮重叠检测。需要已安装 Chrome，或通过 `CHROME_BIN` 指定可执行文件；CI 在部署前自动执行。检查只使用隔离的合成数据，不向 GitHub 执行上传、分叉等写操作。

## 远端仓库被删除或失去权限后的恢复

- 进入工作台、检测更新和上传／同步前会检查已绑定目标，状态保存在项目记录中，并在项目库及工作台显示异常提示。“管理远端目标”可重新检测指定目标或全部目标。账号同源发现独立于这项检测。
- 404 显示为“可能已删除、改名或 Token 无权限”，不据此自动解绑。无效 Token、权限不足、请求限流、网络错误和同名仓库 ID 变化分别提示；临时失败与取消不会自动删除绑定。通过旧地址访问到同一 ID 的改名仓库时更新链接；同名不同 ID 的新仓库禁止自动写入。
- 更新 Token 并重新检测，仅对身份验证成功的目标保存新凭证，供共享该目标的各分支／分叉绑定使用；不改全局或来源凭证。配置导出不包含目标 Token。
- 确认旧目标不再使用后，点击“解除此目标的所有绑定”。确认提示会显示关联记录数量，只解除该远端目标的当前上传、分支和分叉关联；其他目标、项目记录、原始来源、本地源码和历史快照均保留。历史地址不改写到新仓库，也不会从历史副本中自动重新关联已解除的目标。解绑前再次检测，原仓库仍可访问时禁止解绑后重复首次上传。只有确认原仓库删除或原 ID 失效后才解除账号来源记录；远端写入失败会保留待解绑任务，下次创建前必须先完成。
- 解除后可直接“重新设置上传”或“重新创建分叉”，默认带入旧目标名称并允许修改；重新创建的仓库按新 ID 绑定。管理中的旧 Fork 保留项目 ID、来源和本地历史，转为继续跟踪原始来源。新上传继续遵循来源分支和验证成功后才能清理缓存的规则。
- 旧远端版本不可访问且源码缓存已清理时，尝试按保存的源提交恢复，并校验文件清单、hash、类型和模式。源提交也不存在时保留快照、说明需要旧缓存／导出文件或恢复旧仓库，不把未恢复的文件显示为已上传。新仓库只能保留此后产生的 Git 历史，不能凭快照重建用户从 GitHub 删除的全部提交历史。

## 账号去重、跨设备识别与取消日志

- 首次上传、当前分支副本和完整 Fork 共用账号级来源索引。同一来源仓库（优先以 GitHub 仓库 ID 识别）固定一个目标，各来源分支记录自己的目标分支。批量首次上传／分叉跳过已完成或已绑定的同源目标，后续执行“批量更新”或“批量分叉同步”。本来已有但未确认的仓库必须先比较并绑定，首次任务本次不写入项目文件；独立导入仍可保留本地记录，但不能绕过账号去重创建重复目标。
- 应用会在当前账号创建私人仓库 `.gitvault-state`，在 `gitvault.json` 中保存来源、目标仓库 ID、分支映射、已验证提交和首次任务预留。不会保存 GitHub Token 或项目文件，不向完整 Fork 源码加入索引文件。不要公开、删除或手动改写这个记录仓库；被其他用途占用、格式损坏或权限不足时会明确停止写入，不将读取错误当作“没有同源仓库”。
- 同账号在其他设备配置 Token 后，新增原始链接或已记录的目标链接会恢复固定目标；远端提交与凭据吻合时显示“已同步”或“已分叉”，否则显示已绑定／待更新。旧版记录可根据 Fork 上游或托管元数据寻找候选并比较迁移。对于没有来源记录、没有托管标记且被任意改名的旧仓库，GitHub 不提供可靠的同源证据，需要先明确导入并确认绑定。
- Token 需要能读取当前账号仓库，并能创建私人仓库和写入目标及 `.gitvault-state` 内容；限制到少数仓库的凭证必须包含这些仓库并具备相应写权限。没有 Token 时仍可公开拉取，但无法保证跨设备识别；上传或分叉前必须完成账号检查。
- 创建项目之前先以 GitHub 文件 SHA 的比较并交换保存来源预留，避免两台设备同时选择不同目标；冲突时重新合并，不覆盖其他来源或分支。首次任务中断后固定原目标名，若仓库已经出现则先比较；不会换个名称重新创建。后续快照更新仍接续目标最新提交，不强推。账号记录失败时保留已验证远端凭据、固定目标及本地缓存，再次更新只补存记录后继续检查版本。
- 已知目标 404、限流或网络错误都不会自动取消绑定。确认远端已删除后，在“管理远端目标”解除旧目标并完成账号解绑，才重新建立目标；恢复不了的旧 Git 历史不能由浏览器快照重建。
- 批量上传、更新和分叉同步均可“取消剩余操作”。取消会中止正在等待的 GitHub 请求和未开始项目，已验证完成的项目及远端提交保留；已经发送的 GitHub 写请求可能已在服务器完成，取消不表示回滚。重试只处理失败和取消项，同源去重会在重试前再次执行。
- 顶部“操作日志”在本设备持久保存最近 1000 条结果，可筛选失败与未完成、导出 JSON、清空。记录时间、项目、分支、目标、操作阶段、HTTP 状态与失败原因；已知 Token、Bearer 凭证及常见凭证 URL 会隐藏。日志存储不足会提示，账号绑定仍保存在独立账号记录中；本地日志不跨设备同步。

## AI 日志与可选服务端

`npm run dev` 使用本地 Node 服务，AI 功能需要服务端 `GEMINI_API_KEY`（可通过 `GEMINI_MODEL` 指定模型）。纯静态 Pages 未配置 AI 服务时，原日志入口提供明确标注的本地提交摘要。

部署独立 AI 后端时，在构建环境设置 `VITE_API_BASE_URL` 为其地址，并由该后端配置正确的来源访问策略。生产同源 Node 部署可在构建时设置 `VITE_API_MODE=server`；运行时使用 `NODE_ENV=production npm start`。GitHub 或 AI 凭证均不应写入静态构建环境的 `VITE_*` 变量。

## 部署

GitHub Actions 使用 `package-lock.json` 和 `npm ci`；PR 自动检查类型、测试和 Pages 构建，main 更新后部署。Pages 构建路径为 `/Get-Up_GitVault/`。

浏览器、Electron 和 APK 的现有导出入口继续保留。桌面/手机打包应使用适合本地资源的 Vite base（通常为 `./`）；实际写入系统目录仍需要相应原生桥接能力。
